Scrum vs. Kanban Board

Zwei Ansätze, fast gleiches Aussehen

1Das Scrum Board

Sprint Board

  • Gehört zu Scrum und ist zeitlich begrenzt – für die Dauer eines Sprints (z. B. 2 Wochen).
  • Das Team plant zu Beginn fest, welche Tickets im Sprint erledigt werden (Sprint Backlog).
  • ZielAm Ende des Sprints alle Karten auf Done.

2Das Kanban Board

Kontinuierlicher Fluss

  • Funktioniert ohne Sprints oder feste Zeitfenster.
  • Neue Aufgaben werden fortlaufend nachgerückt.
  • FokusRein auf den WIP-Limits (Work in Progress): Überlastung verhindern, Engpässe sofort sehen.

Kanban im Detail

2.1 Das Board und die WIP-Limits

Kanban

japanisch für „Signalkarte“

Kanban ist eine Methode, um Arbeit visuell zu steuern. Die Grundidee: Man macht alle Aufgaben auf einem Board sichtbar. Aufgaben wandern als Zettel (Karten) von links nach rechts – vom Start bis zur Fertigstellung.

Analogie: Ein Whiteboard in der Küche mit den Spalten „Einkaufen“, „Kochen“ und „Fertig“. Jede Aufgabe ist ein Zettel.

1Keine Sprints

Anders als Scrum

  • Kanban kennt keine festen Sprints.
  • Die Arbeit fließt kontinuierlich (Continuous Flow).

2WIP-Limit

Work in Progress = Arbeit in Bearbeitung

  • Legt fest, wie viele Aufgaben gleichzeitig in einer Spalte liegen dürfen.

WIP-Limits

2.1 Arbeit begrenzen

Warum ein WIP-Limit?

Schutz

  • Schützt das Team vor Überlastung.

Fokus

  • Verhindert, dass Aufgaben halbfertig liegen bleiben.

Transparenz

  • Macht Engpässe sofort sichtbar.

Beispiel: Limit 3

Beispiel: Das Limit für „In Bearbeitung“ ist 3. Sind dort 3 Aufgaben, darf niemand eine 4. Aufgabe beginnen. Erst muss eine fertige Aufgabe in die nächste Spalte wandern.

Die Hierarchie

2.2 Vom Großen zum Kleinen

Große Vorhaben sind zu riesig, um sie sofort umzusetzen. Deshalb werden sie schrittweise zerkleinert:

Epic (riesig)→ Feature (mittelgroß)→ User Story (klein & konkret)

Epic

Das Riesengroße

  • Sehr großes Ziel oder Themenfeld, das mehrere Monate dauern kann.

Feature

Die Klammer

  • Zusammenhängende Produktfunktion aus mehreren User Stories mit spürbarem Nutzen.

User Story

Die konkrete Aufgabe

  • Kleine, konkrete Anforderung aus Nutzersicht, in einem Sprint umsetzbar.

User Stories

2.2 & Akzeptanzkriterien

Eine User Story beschreibt eine Anforderung immer aus der Sicht der Nutzerinnen und Nutzer. Sie folgt einem festen Satzmuster:

Als[Rolle]
möchte ich[Funktion]
damit[Nutzen]

Beispiel: Passwort zurücksetzen

User Story

  • „Als registrierter Kunde möchte ich mein Passwort über einen Link per E-Mail zurücksetzen können, damit ich mich bei Verlust des Passworts wieder einloggen kann.“

Akzeptanzkriterien

Zu jeder User Story gehören klare Bedingungen. Erst wenn sie erfüllt sind, gilt die Story als „fertig“.

Die Story ist fertig, wenn …

  • bei Eingabe einer gültigen E-Mail-Adresse innerhalb von 60 Sekunden eine E-Mail verschickt wird. Sie enthält einen Token (einen einmaligen, geheimen Code).
  • der Link nach 30 Minuten nicht mehr gültig ist.
  • bei einer unbekannten E-Mail-Adresse eine neutrale Meldung erscheint (ohne zu verraten, ob ein Konto existiert).
Merke: Ohne Akzeptanzkriterien lässt sich nicht prüfen, ob eine Story wirklich fertig ist – sie machen die Story prüfbar.

INVEST

2.2 Die Checkliste für gute User Stories

Ob eine User Story gut aufgebaut und bereit für die Entwicklung ist, prüft man mit der Eselsbrücke INVEST:

IIndependentunabhängig – möglichst losgelöst von anderen Stories
NNegotiableverhandelbar – Details bleiben im Gespräch
VValuablewertvoll – echter Nutzen für Kunden
EEstimableschätzbar – das Team kann den Aufwand einschätzen
SSmallklein – passt in einen Sprint
TTestabletestbar – Akzeptanzkriterien machen sie prüfbar

Probe aufs Beispiel

✗ „Online-Banking für Privatkunden“

  • Das ist ein Epic – dauert mehrere Monate.
  • S nicht klein genug für einen Sprint
  • E kaum schätzbar

✓ „Reset-Link per E-Mail erhalten“

  • Klein und konkret, aus Nutzersicht formuliert.
  • T durch Akzeptanzkriterien prüfbar (60 s, 30 min, neutrale Meldung)
  • S in einem Sprint umsetzbar
Merke dir:
  • Hierarchie: Epic → Feature → User Story
  • Satzmuster: Als [Rolle] möchte ich [Funktion], damit [Nutzen]
  • Akzeptanzkriterien = wann ist die Story fertig?
  • INVEST = Qualitäts-Check vor der Entwicklung

Fibonacci & Referenz

2.3 Womit wird geschätzt?

Geschätzt wird meist mit der Fibonacci-Folge: 1, 2, 3, 5, 8, 13, … – jede Zahl ist die Summe der beiden vorherigen.

1
2
3
5
8
13

1 + 2 = 3 · 2 + 3 = 5 · 3 + 5 = 8 · 5 + 8 = 13

Warum werden die Lücken größer?

  • Die Lücken wachsen nach hinten bewusst.
  • So diskutiert das Team nicht über unnötige Kleinigkeiten – z. B. ob eine riesige Aufgabe nun 12 oder 13 Points hat.

Die Referenzaufgabe

Das Team legt vorab gemeinsam eine bekannte kleine Aufgabe als Maßstab fest.

1Point

  • Einen Rechtschreibfehler im Hilfetext der App korrigieren.

8Points

  • Die Einbindung einer neuen Kreditkarten-Schnittstelle (Verbindung zu einem externen Bezahlsystem).
Rechtschreibfehler = 1≪Kreditkarten-Schnittstelle = 8

Der Ablauf

  • 1Das Team liest eine User Story gemeinsam durch.
  • 2Jede Person wählt verdeckt eine Karte (1, 2, 3, 5, 8, 13).
  • 3Alle decken ihre Karte gleichzeitig auf.
  • 4Bei großen Unterschieden erklären die Personen mit dem höchsten und niedrigsten Wert kurz ihre Gründe.
  • 5Das Team wählt erneut verdeckt, bis sich alle weitgehend einig sind.

Zusammenfassung & Glossar

Modul 2

Zusammenfassung Modul 2

  • BoardsDas Scrum Board ist zeitlich begrenzt (ein Sprint), das Kanban Board läuft kontinuierlich – beide sehen fast gleich aus.
  • KanbanMacht Arbeit auf einem Board sichtbar, nutzt einen kontinuierlichen Fluss ohne feste Sprints und schützt das Team durch WIP-Limits vor Überlastung.
  • HierarchieGroße Vorhaben werden von Epics über Features zu konkreten User Stories heruntergebrochen.
  • Stories„Als … möchte ich …, damit …“. Akzeptanzkriterien machen sie prüfbar, INVEST hilft bei der Qualitätsprüfung.
  • SchätzenStatt starrer Stunden schätzt man relativ in Story Points (z. B. mit der Fibonacci-Folge).
  • PokerSchätzspiel im Team mit verdeckten Karten. Der größte Wert liegt im gemeinsamen Gespräch zur Aufdeckung von Risiken.

Glossar Modul 2

Akzeptanzkriterium: Klare Bedingung, die erfüllt sein muss, damit eine User Story als fertig gilt.
Epic: Ein sehr großes Projektziel oder Themenfeld, das in mehrere Features und User Stories zerlegt wird.
Feature: Zusammenhängende Produktfunktion (Klammer über mehreren User Stories) mit spürbarem Nutzen für Kunden.
Fibonacci-Folge: Zahlenreihe (1, 2, 3, 5, 8, 13 …), bei der die Lücken nach hinten größer werden. Wird beim Schätzen mit Story Points genutzt.
INVEST: Eselsbrücke und Checkliste für gute User Stories (Independent, Negotiable, Valuable, Estimable, Small, Testable).
Kanban: Methode zur visuellen Steuerung von Arbeit. Aufgaben wandern als Zettel kontinuierlich von links nach rechts – ohne feste Sprints.
Planning Poker: Schätzspiel im Team mit Spielkarten, um verdeckt und ohne gegenseitige Beeinflussung den relativen Aufwand zu bestimmen.
Schnittstelle (API): Verbindung zwischen zwei Systemen oder Programmen, damit diese Daten austauschen können.
Story Point: Einheitsloses Maß für den relativen Aufwand, die Komplexität und das Risiko einer Aufgabe.
Token: Einmaliger, geschützter Code (z. B. in einem Link zum Passwort-Zurücksetzen).
User Story: Anforderung aus Sicht der Nutzerinnen und Nutzer: Als [Rolle] möchte ich [Funktion], damit [Nutzen].
WIP-Limit: Maximale Anzahl von Aufgaben, die gleichzeitig in einer Spalte des Boards bearbeitet werden dürfen.
